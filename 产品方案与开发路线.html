01 / DECISION

先对齐：这次到底要做出什么

参赛版本目标：围绕一个熟悉的欧洲城市、三天旅行，真实完成“需求采集 / 导入已有计划 → 行程体检 → 生成整套旅行手册 → 修改安排 → 同步更新 → 保存可复用经验”。手机网页可操作、可保存、可再次打开。

P0 · 必须完成

完整交付 + 正确更新

引导式需求采集、行程体检、总行程、每日行动卡、短篇背景手册、受约束的行程调整、个人经验复用与数据保存。

P1 · 核心通过后

预算与多模态体验

依次增加票券照片触发操作、同行者偏好协调、90分钟空档推荐、经验纠错复核，再补实际账本、导出和小记。

P2 · 比赛后

完整旅行产品

多城市内容库、翻译中心、预订分佣、退款跟踪、相册视频、多格式交付、多设备实时协作与商业化。

建议默认：米兰三天，包含一个已预订的固定活动与少量核验过的景点。最终城市由团队根据现有资料确定；目的地数量不作为本次完成度指标。

面向谁、解决什么

首批用户是有欧洲自由行计划、希望省心、有体验偏好，但不熟悉当地信息与AI提示方法的中文用户。产品主动提醒其需要考虑什么，并交付能在路上使用的成果。

  • 信息碎片化：景点介绍、订票、地址、交通和注意事项分散，需要用户自行拼接。
  • 使用AI门槛：用户不一定知道该补充哪些条件，也难以检查生成结果是否完整。
  • 计划与现实脱节：晚出门、太累或花费变化后，需要手工修改多处内容。
  • 经验丢失：一次旅行中发现的偏好和踩坑经验，下一次又要重新说明。

成功体验：用户看到“今天下一步做什么”；修改后不必检查每一张旧卡片；下一次安排能反映自己确认过的偏好。

02 / COMPETITIVE REASONING

为什么这样取舍，更适合参赛

证据类型已经观察到的内容我们据此采取的策略
本场海报全场冠军强调完成度、突破性与真实价值；原生智能体赛道强调工具调用、可靠执行与可持续交付。优先把整条真实流程跑通，用变更前后结果和验收记录证明质量。
往届官方杭州场强调经验共享、长记忆、个性化和持续改进。[1]做一次清楚可见的“用户反馈 → 确认经验 → 后续复用”。
往届官方上海作品列表已有 EvoTravel，简介为会学习的AI旅行规划助手。详情页未成功读取。[2]不能只用“AI旅游”或“会学习”解释创新，要具体展示一致更新与成套交付。
媒体线索上海赛后报道描述A2A赛道冠军通过用户互动触发实际行动；未获得完整评审记录。[3]安排观众能看懂的现场操作与明确结果。此推断不能当作官方评分规则。
竞品官方Mindtrip、Wanderlog已有个性化行程、地图、预订整理或预算等功能。[4] [5]少讲功能数量，多证明具体用户完成任务时减少了哪些操作与遗漏。

证据边界：截至本稿，活动官网显示往届页面；深圳场详细评分权重、路演时长、EvoMap接入深度尚未核实。本文的优先级和演示时长均为开发建议，不能据此推算夺冠概率。

评委应能看见

约束被读取、真实工具被调用、修改有依据、固定预订被保留、所有相关页面同步更新、反馈影响后续安排。

观众应能感受到

信息好找、每日卡好看且能用、无需写复杂提示词、现场改一个条件就能得到新的可执行安排。

赛道建议：仍选“原生智能体”。除非多智能体协作本身成为经验证的核心贡献，否则不为增加Agent数量改变架构。

03 / FULL PRODUCT VISION

完整蓝图：旅行前、中、后的全部解决方案

长期愿景保留；参赛范围按优先级推进。不同阶段共享同一趟旅行的数据，避免形成互不相通的小工具。

阶段用户问题完整功能与交付物本次覆盖
探索目的地去哪、看什么、哪里订？按城市与兴趣浏览；90分钟空档推荐；每城逐步扩充至约100个候选地点（不统一宣称“人人必去”）；官网和合作预订入口；小众酒吧、餐厅、俱乐部及当地经验。P0仅收录演示城市约15–25个核验地点；完整目录P2。
确定旅行后如何安排5–15天？还漏了什么？已有行程体检、同行者偏好协调、总计划、住宿与餐厅建议、预订清单、出发准备；景点背景、电影关联、着装要求、习俗、常用语、汇率参考；HTML / PDF / PPT / 备忘录等输出。P0完成三天总计划与简明背景卡；P1一种导出；其余P2。
每天出门前今天怎么走、带什么、先做什么？时间表、交通方式、经核验的公共交通指引、当地语言与英文定位、天气、着装建议、拍照点、入场与集合信息、返回酒店路线。P0每日行动卡；可靠来源支持的内容才展示。
旅行中·调整晚点、太累、下雨，后面怎么办？票券照片确认后锁定预订；区分固定预订与可调整项目；空档推荐；生成备选；说明改动、时间与费用影响；确认后同步更新。P0主线。先覆盖晚出门与减少步行；天气驱动调整P1。
旅行中·预算花了多少、剩多少？手动或拍照录入消费；按城市、日期、类别汇总；欧元与人民币展示；对比预计与实际；辅助选择后续活动。P0预计花费与算术汇总；P1实际账本及小票识别。
旅行中·理解与记录菜单和货架看不懂，想记下当下？菜单、路边说明和超市货架拍照翻译；景点讲解；照片＋感受生成可编辑小记和朋友圈文案。P1轻量小记；独立翻译与全面讲解P2。
旅行后如何整理账单、待办、回忆与经验？发票归档、退款待办与状态；每日相册、时间线视频、“第一顿饭到最后一顿饭”叙事；认识的人、想再去的地点、个人经验沉淀、纠错与复核。P0反馈复用；P1简明旅程回顾；自动视频、退款集成等P2。

退款涉及退票、商家退款或购物退税等不同流程；P2先明确具体类别。没有订单接入时，只能由用户记录状态，不能宣称系统已经完成退款。

04 / PRIORITIES

P0 / P1 / P2：每个功能为什么留、何时做

P0演示成立的必要条件。P1P0验收通过后依次增加。P2本次不承诺，保留在产品路线图。

功能级别保留 / 延后的理由依赖与范围
引导式需求采集P0直接解决用户不会写提示词的问题，决定后续质量。目的地、日期、酒店、同行者、兴趣、体力、预算、固定预订；可跳过未知项。
总行程＋每日行动卡P0体现完整交付与产品审美，能实际陪伴旅行。同一份结构化数据驱动；地址可导航、项目可调整、页面可重开。
简明背景知识手册P0体现体验深度，让你的内容判断进入产品。每个已选景点一张短卡；兴趣相关、可展开、保留来源。
受约束的行程调整P0展示可靠执行，是参赛技术亮点。锁定已订项目；校验时间与交通；展示差异后确认；无法满足时提供取舍。
经验与偏好复用P0回应主办方主题，并展示“反馈产生了什么改变”。少量来源明确的经验；用户确认长期偏好；下一次调用有记录。
预计预算与少量订票链接P0让行程有现实约束与执行入口。估价标时间、币种；未知不填零；点击不算预订成功。
保存、版本、错误状态P0关系到完成度；失败不能破坏原行程。先保存草案，再确认切换；保留上版；测试网络与接口失败。
EvoMap真实接入P0待规则提高生态契合度；技术伙伴在第一阶段验证。先跑通相关工作流检索与复用。是否硬性必做待确认；若赛事要求则是P0交付门槛。
行程体检与修复P0新增主动找出可核验的问题；复用已有校验器，现场前后对比明确。先支持文字和本产品行程；检查时间冲突、交通缓冲、固定预订。复杂PDF导入P2。
票券照片触发行程操作P1-1展示从看懂图片到执行任务；直接连接预订与重排主线。演出票照片→字段确认→锁定活动→体检→调整；不把识别当验票。
同行者偏好协调P1-2评委可参与选择偏好，看到方案取舍。两人、一天、同一设备输入；区分必须与偏好；输出两案，确认后采用。
90分钟空档推荐P1-3体现行中即时决策与当地小众经验。用户提供位置、空闲时长、下一活动；核验营业时间并计算往返与缓冲。
经验纠错与复核P1-4让经验改进过程可追溯，适合展示反馈到复用。提交证据→待复核→人工核验→生效；保留历史，不自动推广未核实结论。
实际消费账本P1-5扩展行中使用，并可辅助预算约束。先手动输入，程序计算；区分已付款与未来预计，避免重复计入。
小票识别 / 更多订单格式P1-6提供现场互动，降低录入负担。复用票券识别组件，再扩展小票与订单格式；必须确认字段后写入，保留手动录入。
PDF或每日卡图片导出P1-7强化交付与分享，适合现场留存。只选一种；标版本和生成时间，说明导出后不自动更新。
照片小记＋简明回顾P1-8让旅行后也有可见成果，作为演示结尾。来自用户实际照片和文字；用户可改；不自动发布。
天气驱动 / 更多异常调整P1-9扩展适应能力，但增加实时数据与校验工作。天气API覆盖期内使用预报；模拟输入必须标明。
多城市目录、酒店餐厅大全P2属于产品覆盖度，短期难证明创新，维护成本高。由内容来源、用户反馈与供应商能力逐步扩展。
全面翻译、视频、多格式、退款集成P2分散主线，且有独立的质量和接口成本。旅行核心稳定、验证用户需求后逐项开发。
联盟分佣、收费、多设备实时协作P2可用于商业模式答辩，本次无需交易系统。联盟资质、归因、用户账户、权限和实际付费验证。

范围冻结规则：如果P0未通过验收，停止增加P1。五个新增方向均已纳入路线图，但不承诺在比赛内全部交付。按P1-1至P1-9推进；时间不足优先延后小记、导出、小票、账本和扩展推荐，保住体检、每日卡、变更校验、保存与经验复用。

05 / CORE SPECIFICATION

功能规格：输入、动作、输出与验收

F01引导用户建立一趟旅行

输入
日期、目的地、酒店地址、同行人数、兴趣、步行接受程度、预算币种与范围、已订活动。预算明确是否包含机票和酒店。
处理
使用简短表单＋必要的补充问题；把“不要太累”转成可由用户确认的条件，不能自行猜测为永久偏好。
输出
可编辑的旅行需求摘要，区分“用户提供”“默认假设”“尚待确认”。
验收
日期冲突被指出；未知酒店能继续但明确路线暂估；任何默认条件可修改。

F02生成总计划与每日行动卡

输入
确认的需求、地点库、营业时间与来源、地图行程时间、固定活动与预计费用。
处理
模型提出安排，程序检查时间重叠、固定活动、交通缓冲与预算完整性；缺少数据的项目标记待核验。
输出
总行程；每一天的行动卡；预订待办；预计预算。卡片展示时间、目的地原名、地址、交通、导航、入口与提醒。
验收
总计划与卡片引用同一项目；地址链接有效；不能把无法确认的票价和库存写成确定事实。

每日卡的阅读顺序

  1. 今天的主题与首个行动。
  2. 按时间排列的路线和交通。
  3. 已订 / 待订标识与预订入口。
  4. 出门前提醒、文化背景和附近选择。
  5. 预计费用、数据更新时间与修改入口。

F03按兴趣生成简明背景手册

输入
实际选中的景点、用户兴趣、可信背景资料与适用提醒。
处理
每个地点先生成“为什么值得看、重点看什么、现场注意什么”；电影关联等资料在有可靠依据时补充。
输出
行程内可展开的文化背景卡；汇总为手册视图。按兴趣改变重点，避免长篇通用百科。
验收
无关景点不混入；事实可追溯；着装要求与个人建议分开；手册随行程增删同步变化。

F04接收变化，生成受约束的新安排

触发
“晚一小时出门”“下午少走路”“这个地方不想去了”。P0先覆盖明确的时间和偏好修改。
处理
解析影响范围 → 读取固定预订 → 查询必要交通信息 → 产生新草案 → 校验 → 展示前后差异 → 用户确认 → 保存新版本。
输出
修改项目、原因、交通与预计费用差异；总行程、行动卡、背景卡同步更新。
验收
已订活动不被悄悄移动；无解时解释冲突并提供选项；失败保留旧版本；确认前不覆盖。

F05保存、筛选并复用经验

输入
用户确认的长期偏好，或具备地点、时间、条件与来源的亲历经验。
处理
先区分临时状态、个人偏好、地点事实与通用方法；只将适用且仍有效的内容用于后续推荐。
输出
“这次采用了哪些经验”的说明；下一次生成能体现已确认偏好；用户可修改或删除记忆。
验收
背包客与大行李旅客可得到不同建议；一次抱怨不直接写成永久规则；没有复用记录不声称已经学习。

F06 · P0行程体检与修复

输入
已有计划文本或本产品行程、交通资料、固定预订。
处理
解析为活动列表并由用户确认；复用时间与交通校验器；按问题展示依据、影响和修复候选。
输出
体检结果分为已验证冲突、待核验信息、偏好提醒；确认修改后生成新版本。
验收
确定的时间冲突不能漏报；资料不足不判定正常；修复后复检；营业时间检查仅在有有效来源时启用。

F07 · P1-1从票券照片触发行程操作

输入
演出票照片；可见的日期、时间、场地、人数等信息。
处理
识别字段→用户补齐和确认→查找场地→保存固定活动→运行体检→提出重排→确认应用。
输出
一个实际写入行程的固定活动，及与其一致的每日卡；重复票券先提醒。
验收
模糊日期不猜测；区分开门与开演时间；不宣称票券有效；重复上传不重复入账或建活动。

F08 · P1-2同行者偏好协调

输入
两人的必须条件、兴趣偏好、可妥协项；同一设备填写。
处理
优先满足双方硬约束；冲突需选择；生成两套解释清楚的候选，必要时提出分开活动与会合地点。
输出
条件满足表、未满足项、两案差异；选定后接入现有行程与版本系统。
验收
不编造满意度百分比；不可满足的条件明确列出；分开活动为可选提案，不自动采用。

F09 · P1-3现在有90分钟，附近能做什么

输入
用户提供或授权的位置、空闲时长、下一固定活动的地点和到达要求。
处理
检索附近候选→核验开放信息→计算去程、停留、前往下一站及缓冲→按兴趣和预算排序。
输出
最多三个可行选项，显示总用时、出发截止时间、费用依据和推荐理由；确认后加入行程。
验收
总用时在空档内；包含到下一站的路程；无可行结果时明确说明；位置和交通缺失时请求补充。

F10 · P1-4经验纠错、复核与后续使用

输入
用户指出旧入口、旧时间或不适用经验，并提供照片、链接或文字说明。
处理
记录原经验与证据→设为待复核→核验来源与适用范围→审核通过后生效→保留变更历史。
输出
可查看的反馈状态与新旧经验；后续计划显示实际引用的版本。
验收
待复核信息不作为确定事实传播；个人口味不改写公共事实；不自动改动他人已确认行程；外部发布另行授权。

“学习”的准确含义：本版是保存经确认的偏好与经验，并在后续任务中检索复用；不宣称训练了新模型，也不把私人订单、照片或行程自动发布到公共经验网络。

06 / USER WORKFLOW

用户从第一次打开，到旅行结束

  1. 建立旅行 P0

    选择城市与日期，或粘贴已有计划 → 提供酒店、兴趣、预算与固定安排 → 补充关键缺项 → 确认需求摘要。P1可录入两位同行者的硬条件与偏好。

    保存为草稿；退出后可以继续。未知信息明确标记。

  2. 收到第一套成果 P0

    体检初稿并确认修复 → 浏览总计划 → 打开每日卡 → 阅读背景手册 → 查看待订项目和预计花费 → 修改不合适的安排。

    生成中显示实际进度；失败提供重试与已有内容，不能只留下空白页。

  3. 完成必要预订 P0手动

    点击可信订票入口 → 在供应商处完成预订 → 返回录入日期与状态 → 确认后锁定活动。

    跳转不代表成交；未接入库存，不提供实时有票保证。P1先增加演出票照片识别；确认字段后加入固定活动，再体检和重排。

  4. 今天出发与途中调整 P0

    查看今日卡 → 打开导航 → 输入变化 → 查看新旧安排与冲突 → 确认新版本 → 继续旅行。

    P1可使用“90分钟空档”推荐插入可行体验。临时偏好优先影响当前日期；需要长期记住的内容单独确认。

  5. 记消费与当下感受 P1

    手动输入或拍照 → 确认金额、币种、日期 → 更新账本 → 需要时请求更符合剩余预算的安排；照片＋一句感受生成可编辑小记。

    账本写入与修改行程分开确认。小费、多人付款和重复小票必须能人工修正。

  6. 回顾与下一次复用 P0经验P1回顾

    确认值得保留的偏好和经验 → 汇总实际记录与照片 → 留下想再去的地点 → 下一次创建旅行时复用适用内容。

    P1支持经验纠错并查看复核状态；未经复核不作为确定事实推广。相册视频、退款集成等完整旅行后功能属于P2。

07 / IMPLEMENTATION

给技术伙伴：如何实现，哪些工作交给谁

建议第一版：响应式网页＋服务端模型调用＋轻量数据库。沿用团队熟悉的技术栈，不为参赛引入不必要的复杂架构。Codex辅助开发、调试和测试；产品运行时仍需模型服务、存储与必要的外部数据接口。

网页输入→旅行任务服务→模型＋工具→结构校验＋约束检查→版本保存→卡片与手册渲染

模型负责理解与提案

提取需求、选择候选活动、提出重排方案、生成中文说明与文化内容。通过受控工具获取资料，输出符合约定结构的数据。

程序负责计算与一致性

行程体检、硬条件满足检查、空档时间计算、金额汇总、币种处理、时间冲突、固定项目锁定、版本写入、权限与链接校验。卡片和手册从同一版本生成。

最小数据对象

对象关键字段 / 约束

关键工具与降级方式

依赖正常使用失败或尚未接入
地点与官网信息检索可信页面＋已整理的地点库。使用注明核验时间的资料；标记待确认，不杜撰营业时间。
地图与路程时间查询坐标与指定交通方式的预计用时。使用事先核验的演示路线并标记非实时；不声称实时路况。
天气 / 汇率天气在预报覆盖期内调用；汇率附时间。天气缺失就不确定推荐；估算汇率明确标注，不视为银行卡结算价。
图像识别（P1）识别金额或订单字段，用户确认。保持手动输入可用；失败不创建消费或预订记录。
EvoMap先验证相关recipe的检索、读取与实际复用；按权限起草或发布通用工作流。[6]无相关资产时如实说明；本地经验库可支持产品流程，但不能冒充已完成EvoMap集成。

部署底线：密钥保留在服务端；公开演示使用去标识化数据；多人试用隔离各自旅行。未做账户系统时，使用不含私人信息的演示会话，避免所有人写入同一份旅行。

状态一致性：生成和调整先落为候选版本，校验通过且用户确认后再切换。对重复点击防重入；过期版本不能覆盖较新版本。地图失败时保留原行程。

08 / BUILD SEQUENCE

逐步推进：每一步都有交付与通过条件

以下是工作顺序，不是对工时的承诺。按已确认的比赛开发窗口安排；赛前可准备到什么程度遵循主办方规则。

步骤要做的工作主要负责人交付物通过后才进入下一步
0 · 范围与规则确认赛道与EvoMap要求；确定演示城市；冻结P0与一个核心变化场景；试跑关键API。产品＋技术一页范围表、素材清单、接口验证结果。知道外部依赖是否可用；不可用时已有明确方案。
1 · 数据与样板整理地点、来源、背景卡、两种用户条件和固定活动；定义旅行与版本字段。产品主导，技术校验一份高质量人工样板＋结构化示例数据。内容能核验；足以支撑三天演示，不靠临场编信息。
2 · 可用网页建立旅行、总计划、每日卡、背景手册；先用明确标注的样例数据做显示与保存。技术＋Codex；产品验收手机网页第一版，刷新可重开。核心页面可操作；样例与真实生成状态区分清楚。
3 · 真实生成接模型与资料工具；结构化输出；程序校验；生成并保存第一版旅行。技术＋Codex真实输入或已有行程到体检与整套交付的可运行流程。至少两组需求能生成不同且可解释的方案；已导入的活动能够体检。
4 · 调整与一致性实现行程体检、固定活动锁定、重排、差异展示、确认、版本保存与失败回退。技术主导；产品测试参赛核心演示：改条件后整套更新。固定预订、时间、版本、费用检查通过；不能只改文字。
5 · 经验复用确认偏好、按条件检索经验、展示引用；按规则完成EvoMap接入。共同完成同一需求加入经验前后的结果对照。经验可追溯、有适用条件；实际影响结果，有复用记录。
6 · P0验收完整功能测试、真实用户试用、网络失败与多设备检查；修复阻断问题。产品＋技术测试记录、用户反馈、缺陷列表。核心流程稳定；否则不增加P1。
7 · 选择P1按优先级增加票券操作、两人协调、空档推荐、经验复核，再考虑账本、导出、小记；一次只加一个并回归核心流程。按剩余时间分配通过验收的增强功能。新功能不损害P0；未完成的功能不放进现场承诺。
8 · 冻结与路演冻结功能；整理证据；准备讲解、演示数据、备用录屏与本地快照。产品主讲，技术保障可访问原型、演示脚本、技术说明、真实指标。连续演练完成；演示数据和备用内容均有标识。

你承担的关键工作

挑选真实旅行场景；提供内容样板与亲历经验；定义“好看、好找、走得通”；试用验收；路演表达与用户反馈。

技术伙伴与Codex

技术伙伴确定数据和接口边界、审查关键逻辑、处理部署；Codex按任务实施代码、运行检查、修复与整理文档。每个任务必须附验收条件。

建议投入顺序：核心生成与调整 → 经验复用 → 测试稳定 → 视觉完善 → P1。预留总开发窗口最后约四分之一用于修复、试用与路演；这个比例是排期建议。

09 / VALIDATION

用什么证明：好用、可靠、有差异

以下是拟定的验收标准，尚未执行。测试结果必须记录成功与失败，不把目标写成已实现指标。

测试操作通过条件
T01 首次创建输入完整需求生成三天计划。总计划、三张每日卡与对应背景卡均可打开；生成失败有明确状态。
T02 固定预订晚一小时出门，保留下午固定活动。固定活动时间与状态不变；路程和缓冲可行；无解时不强行生成。
T03 全局一致确认一次重排，再看各个页面。日期、顺序、地点与预计费用来自同一版本；旧内容不残留为当前计划。
T04 失败恢复工具超时或生成结果不合格。原计划未丢失，可重试；不显示假成功。
T05 保存与防重刷新、重复点击确认、打开旧版本。不生成重复项目，不用旧版本覆盖新版本；可以回到上一版。
T06 条件化经验同一地点分别用于背包与大行李用户。只有条件匹配时才采用经验；展示来源和适用原因。
T07 临时与长期偏好输入“今天太累”，再建立新旅行。未经确认不永久降低所有旅行强度；确认后的偏好能复用。
T08 资料可信度检查抽取的地址、时间、价格与链接。动态内容有时间与来源；缺失明确标注；没有虚构库存或预订成功。
T09 手机操作在窄屏完成创建、浏览和调整。无需缩放才能读正文；关键操作可触达；无横向溢出或遮挡。
T10 预算（P1）修改金额、币种，重复上传一张小票。用户确认后入账；算术正确；有重复提醒；估算与实际不重复计入。

新增功能验收

测试操作通过条件
T11 行程体检（P0）导入有时间冲突、交通缓冲不足和未知资料的计划。分别指出已验证问题与待核验项；确认修复后复检；无资料不报“全部正常”。
T12 票券动作（P1）上传清晰、模糊和重复演出票照片。字段需确认；固定活动正确加入；模糊字段待补充；重复票不重复创建。
T13 同行协调（P1）两人兴趣不同，再加入无法兼容的硬条件。提供可解释的候选；冲突需人工取舍；不声称无依据的满意度。
T14 空档推荐（P1）设置90分钟空档与下一固定活动。去程、停留、到下一站与缓冲之和符合限制；无可行项目如实说明。
T15 经验复核（P1）提交一条错误反馈，再提交有来源支持的纠正。未通过信息不作为事实复用；核验后生效；历史可查；私人信息不公开。

三份有说服力的证据

用户证据

邀请3–5位目标用户独立完成任务。记录完成率、耗时、需要帮助的次数与主要卡点；样本小，仅作为探索结果。

可靠性证据

用同一组变更案例记录固定项目保留率、冲突数、页面一致性、失败恢复情况和实际响应耗时。

对照证据

给同一模型相同需求与资料，对比直接聊天和产品流程；使用合理提示，不人为弱化基线。记录遗漏与用户额外操作。

建议发布门槛：P0关键验收全部通过；新增P0行程体检也必须通过；同一演示连续成功三次；更换至少一组输入仍能完成；存在未解决问题时准确披露。此门槛是内部质量要求，不是官方评分标准。

核心答辩：为什么不直接问AI？

我们主动补齐旅行条件，并把结果保存为统一的旅行数据。一次修改会触发约束检查和所有相关交付物更新。用相同任务的实际对照结果说明节省了哪些操作。

核心答辩：什么是你们的贡献？

旅行任务设计、经验适用条件、固定预订与版本机制、中文行动卡与文化交付，以及验证这些能力的真实案例。使用Codex开发如实说明。

演示诚信：实时调用、缓存资料、人工整理信息和模拟事件分别标记；备用录屏明确说是录屏；不声称已经自动订票、真实退款或自动训练模型。
