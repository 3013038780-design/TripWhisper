# TripWhisper｜第一步：产品需求定义

版本：v0.1，2026-09-09。用途：团队讨论与范围确认。依据：此前产品构想及本次两张讨论笔记。本文件是建议稿，优先级调整尚待团队确认；不代表功能已实现，也不代表已经核实本场比赛评分标准。原 HTML 方案保留，本稿聚焦开发前的产品定义。

## 1. 我们要做什么

一个面向中文欧洲自由行游客的旅行网页应用：把目的地信息、个人偏好和真实旅行经验，变成可以直接照着走的每日安排；旅行发生变化时，帮助用户调整；旅途中的记录经用户确认后，沉淀成回忆与可复用经验。

核心承诺：用户不需要会写提示词，也不用自己拼接多轮 AI 回答，就能知道“今天去哪、为什么适合我、怎么去、在哪里订、变化了怎么办”。

第一阶段形式：手机优先、电脑可用的网站。官网订票通过外链完成；支付、库存和订单确认由对应网站处理。我们整理入口、提示准备事项和记录预订约束。

## 2. 第一批用户与使用场景

建议先服务：已经决定去欧洲自由行，行程约 5—15 天，中文为主、不熟悉当地交通及预订系统、愿意自己出行但不擅长深度使用 AI 的游客。

用户第一次打开产品时，至少已有目的地意向或一份粗略行程。尚未决定去哪个国家的用户可以先浏览，但不作为第一版核心验收对象。

首个演示建议只覆盖一个熟悉且能核实资料的城市及周边，例如米兰与科莫湖。具体城市由团队根据知识储备确认。“支持输入任何城市”和“有可靠内容覆盖”必须区分。

高端私人定制与面向文旅机构的服务，是两个不同商业假设。第一版先验证个人游客是否愿意实际使用，不同时建设两套业务。

## 3. 需求拆解：问题、解决方案与用户得到什么

| 真实问题 | 产品解决方案 | 用户可见的结果 |
| --- | --- | --- |
| 不知道一个城市有哪些区域，景点怎么分布 | 城市速览：地图、区域关系、精选地点与简短介绍 | 1—2 分钟建立方向感，知道住哪里、玩哪里 |
| 不清楚自己的偏好，也不知道 AI 能帮什么 | 标签选择加少量情境题，生成可修改的偏好摘要 | 一张“我们理解的你”，由本人确认 |
| AI 的长篇攻略难以执行 | 总行程与每日行动卡，共用同一份行程数据 | 时间、地点、交通、费用估计、订票入口集中呈现 |
| 外国官网分散，语言与规则难懂 | 经核实的官网入口和预订要点 | 知道去哪订、是否限时入场、需要准备什么 |
| 小众体验缺少有用信息，通用攻略忽略细节 | 带来源和适用条件的经验卡 | 看见行李、坡道、排队、季节等实际限制 |
| 天气、体力和临时闭馆使计划失效 | 在保留已订项目的条件下重新安排 | 看见变更原因、受影响项目与替代方案，并确认应用 |
| 照片和感受零散，回家后忘了细节 | 图文或语音记录，整理为当天小记 | 可编辑的回忆草稿，选择后导出 |
| 一次旅行的教训没有积累下来 | 结束后回顾，区分个人偏好和地点经验 | 下次规划参考已确认的偏好；地点经验单独复核 |

“情感需求”落实为：被理解、少焦虑、保留属于自己的记忆。“社交需求”落实为：可选的交流开场建议与分享草稿，而非第一版建立陌生人社交网络。

## 4. 第一版用户流程

### 第一步：告诉我们这趟旅行的基本情况

输入目的地、日期或天数、人数、预算币种及预算范围、住宿位置、已订项目、体力或行动限制。未确定的信息可以跳过，产品明确显示暂用的假设。

用 3—5 道情境题辅助判断，例如：时间有限时更愿意排队看名作，还是步行探索街区？带行李时能接受多少步行？不要把题目结果当成不可修改的人格结论。

输出：偏好摘要和待确认信息。用户修改或确认后再生成计划。

### 第二步：快速认识目的地并选择想去的地方

展示城市区域概览和少量精选地点，兼顾热门、小众、博物馆、餐饮与人文。首城建议人工核实 10—20 个地点，不以“每城 100 个必去”作为首版任务。

每个地点说明：适合谁、预计停留多久、预算范围、限制条件、资料来源与核实日期。用户可以收藏或排除。

### 第三步：得到能执行的计划

先展示总行程，再进入每日行动卡。每张卡包含：时间段、地点及当地名称、地址、地图导航入口、交通方式和估算时长、活动说明、预订状态、官网入口、费用估计及简短背景。

复杂背景内容按需展开。长背景书、电影推荐、当地常用语等围绕当前地点呈现，避免一次输出大量材料淹没当天行动。

天气、票价、开放时间：只有取得相应数据时才显示为已查证信息；否则标注未核实。不要把模型推测写成实时结果。

### 第四步：旅行发生变化时调整

用户主动输入“今天累了”“下雨了”“这个馆没开”等变化。系统先展示调整建议，说明保留了哪些预订、改变了哪些安排、是否存在冲突。

用户确认后更新总行程与每日卡，并保存上一版本。无法满足全部约束时，明确让用户选择取舍，不能偷偷挪动已订时间。

### 第五步：留下感受并带到下一次

一天结束时，用户可进入回顾页上传照片、输入一句感受；系统生成小记草稿和经验候选。首版采用用户主动进入的方式，不承诺后台自动追问或推送。

用户分别选择：保存私密回忆、导出分享文案、更新个人偏好。地点经验经本人同意和资料复核后才进入共享内容库；公开分享由用户操作。

## 5. P0 / P1 / P2：先做什么及原因

P0 为首个可运行闭环；P1 为闭环通过后增强；P2 为验证需求后扩展。表中“保留”是产品建议，不是已确定的比赛得分项。

| 优先级 | 范围 | 保留或延后的原因 |
| --- | --- | --- |
| P0 | 基础信息、偏好确认、已订项目录入 | 让规划依据可见，支持后续约束检查 |
| P0 | 单城速览、精选地点、人工核实的经验卡与官网外链 | 同时回应信息分散和私人经验的价值，控制资料质量 |
| P0 | 总行程、每日行动卡、简短背景介绍、地图跳转 | 构成实际可用的旅行交付物，超出普通聊天回答的组织方式 |
| P0 | 用户触发调整、固定预订保护、版本恢复 | 可在路演中直接验证智能体是否会处理变化 |
| P0 | 轻量回顾：文字感受、小记草稿、确认一条偏好并用于下次生成 | 用小范围实现经验积累；照片、语音识别后置 |
| P1 | 照片与语音记录、票券识别、拍照记账、预算差额、汇率换算 | 有价值，但引入识别纠错、敏感信息处理与数据接入成本 |
| P1 | 同行者偏好协商、空档推荐、菜单翻译、交流开场建议 | 丰富旅行中体验，需要先确认核心使用频率 |
| P1 | PDF 导出、背景长读、电影推荐、多种分享文案风格 | 主行程数据稳定后再扩充交付格式，避免重复维护 |
| P2 | 大量城市和每城百个地点、社区共创、内容商家后台 | 持续审核与运营负担较高，尚未验证供给模式 |
| P2 | 统一支付或代订、退款跟踪、全自动相册视频、跨平台发布 | 依赖交易系统、平台接口或复杂媒体处理，首版收益待验证 |
| P2 | 原生 App、小程序、高端人工定制服务体系、To B 产品 | 用户、交付方式和商业成本差异大，另行验证 |

本稿建议把“最小回顾与偏好复用”放入 P0；此前 HTML 将较完整的小记放在后续。本次只前移文字闭环，不前移完整图像、语音和视频制作。

## 6. 私人经验如何成为可信的产品内容

每条经验至少保存：地点、经验正文、亲历或其他来源、发生时间、适用条件、核实状态、是否允许公开。

例如“科莫湖住宿拖行李很困难”应拆成具体地点和路线：哪家住宿或哪个区域？离码头多远？是否有坡道、台阶和石板路？是否有接送？不要直接推广为“科莫湖岛上都不适合住”，也要核实所说地点究竟是岛屿还是湖边城镇。

小众酒吧、俱乐部和餐厅同样需要核实营业状态、预订方式与适用人群。信息少不能自动等同于值得推荐。

这部分可能形成竞争力，但前提是确实改变了安排：例如知道用户带大箱子后避开难走路线，并展示原因。仅把经验文字放进知识库还不够。

## 7. 核心验收：怎样才算做出来

1. 一个不懂提示词的测试者，可以完成基本信息、看懂并修改偏好，得到第一份计划。
2. 每日卡中地点可打开导航；订票按钮指向核实的官网；未核实的时间和价格有明确标识。
3. 同一天没有明显重叠安排，交通留出时间；已订项目的日期与时间保持不变。无法生成可行计划时展示冲突。
4. 输入“今天少走路”后出现具体变化及原因；确认后总行程与每日卡一致，并能恢复上一个版本。
5. 确认一条个人偏好后，下一次生成能展示它如何影响推荐；删除偏好后不再使用。
6. 生成失败时保留已输入信息；用户可以重试或继续查看上一版计划。

首轮建议找 5 位符合目标画像的用户观察使用。记录完成时间、求助次数、官网跳转成功情况、明显行程错误和是否愿意实际带着使用。小样本用于发现问题，不据此宣称市场需求成立。

## 8. 尚未成立的假设与验证方法

| 假设 | 如何验证 |
| --- | --- |
| 用户需要完整流程，而不满足于直接问 AI | 让用户分别用普通聊天和本产品完成同一旅行任务，比较求助次数、耗时和可执行性 |
| 私人经验具有独特价值 | 观察经验卡是否使用户改变住宿、交通或活动选择，追问具体原因 |
| 偏好题能改善推荐 | 检查用户确认后的推荐接受度，并与仅用简单标签的流程比较 |
| 用户愿意每天记录或被询问 | 小规模试用中观察主动记录与拒绝情况，默认可以跳过 |
| 用户愿意付费 | 展示具体交付样例与价格方案，询问真实购买选择；把实际付费与口头喜欢区分 |
| 携程、飞猪等没有满足该需求 | 后续做实际产品体验和用户访谈；不能从笔记推断它们没做，更不能推断它们因亏损放弃 |

“nomadic”“可可出行”等笔记中的竞品名称需先确认准确产品及网址，再比较同一任务的完成方式。本稿不把未核实的竞品判断写成结论。

## 9. 从需求推进到开发

1. 产品对齐：确认首批用户、首城、上述核心承诺和 P0。产出一页范围表；暂不纠结收费接口和技术框架。
2. 内容与场景准备：建立首城地点资料、预订示例及 3 个真实问题案例。用用户亲历资料时先去除姓名、订单号等无关个人信息。
3. 可点击原型：信息输入 → 城市速览 → 总行程 → 今日卡 → 变更确认 → 回顾。用同一案例走通，不以页面数量验收。
4. 技术闭环：先保证数据保存、外链、约束检查和版本一致，再接入生成能力。所有视图读取同一份结构化行程。
5. 用户试用：根据第 7 节验收，优先修复无法执行、看不懂和数据错误的问题。
6. 路演准备：展示一位带行李的游客，从确认偏好到生成计划，再到体力变化后的调整，最后把确认的经验用于下一次规划。明确哪些是真实接入、哪些是预设演示数据。

参赛竞争力的建议重点：问题真实、用户能操作、调整结果可信、经验复用可见。具体赛道、评分权重、指定技术要求需另行核实，不能用功能数量替代参赛适配判断。

## 10. 本次团队会议要做出的决定

- 是否接受“可执行的每日旅行安排与调整”为主体验，记录分享作为轻量闭环？
- 首个城市选哪里？现有亲历资料中哪些可以核实并用于演示？
- 团队人数、可投入时间、比赛截止时间是什么？据此缩减 P0，而不是提前承诺所有功能。
- 谁负责内容核实与体验验收，谁负责实现与发布？即使用 Codex 开发，也需要明确这两类责任。

会议产出应是“首城 + 一个完整用户案例 + 确认后的 P0 + 负责人”，而不是继续增加功能清单。
